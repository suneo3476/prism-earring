このドキュメントは、prism(コードネーム。配布名は「カツオ」)の実装を、Unity/UE 向けオーディオプラグイン開発の経験を持つ読者向けに解説するものである。ソースコードの大部分は AI が生成したため、開発者自身も構造を把握し切れていない部分が残っている。そこで本書は、実際のソースファイルと関数名を根拠に、アプリの全体構成・呼び出しフロー・ピッチシフトのアルゴリズム・数値検証・設計からの逸脱を順に説明する。

読み終えたときに、オーディオコールバックのどの行が何をしているかをソースへ戻って追えるようになることを目標にする。参照した主なファイルは dsp/include/prism/PitchShifter.h、android/app/src/main/cpp/*、android/app/src/main/java/dev/saku/prismearring/*.kt、web/wasm/prism_bridge.cpp、web/prism-worklet.js、verify/verify.cpp、リポジトリ直下の README.md である。

Chapter 1

全体構成

prism が DSP コア・接着層・UI の3層に分かれており、Android と Web の両方が同じ DSP コアを呼び出す構成になっていることが分かる。

prism の目的は、マイクで拾った音を約 -89 セント(セントとは音高の単位で、半音を100等分した値を指す。-89セントは半音よりわずかに狭い下方シフトに当たる)ピッチシフトし、イヤホンからほぼ遅延なく聴かせることにある。この目的を Android アプリと Web デモの両方で実現するため、prism はアルゴリズム本体を1箇所に集約し、そこへ薄い接着層を被せるという構成を取っている。

制約は2つある。第一に、DSP コアはプラットフォームに依存してはならない。Android と Web で同じ計算結果を再現する必要があるためである。第二に、接着層はプラットフォーム固有の API(Oboe、AudioWorklet)を持つが、アルゴリズムそのものには手を入れてはならない。手を入れてしまうと2つの実装が少しずつ乖離していくためである。

この制約を満たすため、prism は図1のような3層構造を取っている。最下層の DSP コアは dsp/include/prism/PitchShifter.h 1ファイルに実装された namespace prism の class PitchShifter であり、C++17 標準ライブラリ以外に依存しない。中間層の接着層は、Android では AudioBridge.h・PrismEngine.{h,cpp}・jni_bridge.cpp が、Web では prism_bridge.cpp(Emscripten でビルドして prism.wasm にする)と prism-worklet.js が担う。最上層の UI 層は、Android では MainActivity.kt・PrismService.kt・Params.kt などの Kotlin 群が、Web では index.html と main.js が担う。図中の矢印は依存の向きを表しており、UI 層は接着層を、接着層は DSP コアを呼び出すという一方向の依存になっている。

なお Web 版には、WASM のロードに失敗した環境向けに PitchShifterJS という JavaScript 実装が prism-worklet.js 内に同梱されている。これは PitchShifter.h の算術を1対1で書き写したフォールバックであり、本番経路は常に WASM 側である。

この構成が崩れていないかどうかは、DSP コア側では検証プログラム(verify/verify.cpp。4章で詳しく述べる)がソースコード中に FFT やロックが混入していないことを機械的に確認する形で担保している。接着層側は Android・Web それぞれのビルドとテストで確認する。

prism は DSP コアを1つだけ持ち、Android と Web はそれぞれ別の接着層からそれを呼び出す。接着層を変えてもアルゴリズムは変わらないため、Android と Web で聴こえ方が一致する。

この構造により、次章以降で Android の呼び出しフローと DSP コアのアルゴリズムを別々に読み進めることができる。

Chapter 2

Android の呼び出しフロー

prism-earring が起動してから定常的に音を処理するまでの流れ、パラメータをスライダーで変えたときに何が起きるか、そして他アプリの音を拾う捕獲経路がどうマイク経路と混ざるかが分かる。

Android 版の目的は、画面を閉じても、他のアプリに切り替えても、常駐して処理を続けることにある。

この目的のため、エンジンの所有者は Activity ではなく ForegroundService(バックグラウンドでも OS に殺されにくい Android の常駐サービス形態を指す)である PrismService に置かれている。MainActivity は PrismService に bind して状態を読み、パラメータの変更を Service 経由で流し込むだけであり、エンジンを直接持たない。もう1つの制約は、CLAUDE.md が定める「オーディオコールバック内でヒープ確保・ロック・I/O・例外を行わない」というリアルタイムオーディオの鉄則である。この鉄則により、パラメータの受け渡しは std::atomic 越しにしか行えず、UI スレッドとオーディオスレッドの間にロックは一切現れない。

起動〜定常状態のフロー

UI(MainActivity ほか, Kotlin) PrismService(常駐サービス) ネイティブ層(PrismEngine / AudioBridge / JNI) Oboe / OS(オーディオストリーム) DSPコア(PitchShifter, 3章で詳説)

ユーザーが開始ボタンをタップすると、MainActivity.requestStart() が RECORD_AUDIO 権限を確認したのち、ContextCompat.startForegroundService(ACTION_START) で PrismService を常駐化する。PrismService.startProcessing() は前景化(startForegroundCompat())を先に済ませてから、Params.applyTo(engine) で保存済みのパラメータをエンジンへ流し込み、NativeEngine.start() を呼ぶ。ここから先は JNI(Java Native Interface の略で、Kotlin から C++ の関数を呼ぶための Android の橋渡し機構を指す)を1回だけ越えて nativeStart(handle) が呼ばれ、ネイティブ側の PrismEngine::start()(実体は startLocked())へ入る。

startLocked() はまず出力ストリームを1度試し開きしてサンプルレートとバースト長(Oboe が1回のコールバックで受け渡す最小フレーム数の単位を指す)を取得し、それを使って出力ストリームを本開きする。デバイスは Exclusive(占有)から Shared(共有)へ、指定デバイスから自動デバイスへの順に条件を緩めながら openOutput() が試行する。入力ストリームは configureInput() が Unprocessed(AGC・ノイズ抑制・AEC をすべて無効化する入力プリセットで、ピッチを最も素直に通す)から VoiceRecognition、Generic の順に試す。両方のストリームが開いたら、AudioBridge::prepare() が唯一のヒープ確保区間として PitchShifter を2本(マイク経路用と捕獲経路用)確保する。最後に inputStream_->requestStart() と outputStream_->requestStart() が呼ばれ、入力を先に走らせてから出力を開始する。

prism-earring は出力コールバック駆動の全二重(全二重とは送信と受信を同時に行える通信形態を指し、ここではマイク入力とイヤホン出力を1つのコールバックで同時に処理することを意味する)という構成を取っている。入力ストリームは自分のコールバックを持たず、出力ストリームのコールバックである onAudioReady(outputStream, data, numFrames) の中から input->read(scratch, numFrames, 0) を呼んで読み出す。これは Oboe の LiveEffect サンプルと同じ構成であり、入力と出力それぞれにコールバックスレッドを立てて同期を取るよりずっと単純になる。

onAudioReady() は毎回 AudioBridge::nextStep() を呼んで今回やることを決める。起動直後は DrainInput(たまっていた古い入力を8コールバック連続で捨て切る)、続いて BuildCushion(逆に数バースト分読まずに入力をためる)を経て、ようやく Render に入る。Render では読み込んだ入力を AudioBridge::render() に渡し、内部で非インタリーブ形式(左右チャンネルを別々の配列に分けた形式を指す。Oboe から来るインタリーブ = LRLRLR... 形式と対比される)へ変換したのち、PitchShifter::process(inPlanar_, outPlanar_, chunk) が呼ばれる。ここが DSP コア本体の呼び出しであり、詳しい中身は3章で説明する。処理結果は mixChunk() でゲインとソフトクリップ(信号が一定振幅を超えた分だけ tanh で滑らかに丸め、±1.0を超えさせない処理を指す)を経てからインタリーブに戻され、出力バッファへ書き込まれる。このループが起動同期を終えると synced_ が true になり、PrismService の1秒ごとの poller がそれを isSynced() 経由で読み取って画面の「稼働中」表示を更新する。

この一連の流れが崩れていないかどうかは、Android 側では実機での起動・停止の繰り返しと、AudioBridge::underrunCount() / inputErrorCount() などの診断カウンタで確認する。DSP コア呼び出し自体の正しさは4章のオフライン検証がソースコードから独立に保証する。

起動から定常状態までは PrismService が前景化とエンジン起動を仲介し、その先はネイティブ層の状態機械(Drain→Cushion→Render)が担う。

オーディオコールバックの中で実際に呼ばれる関数は onAudioReady → nextStep → render → shifter_.process という一直線であり、途中に確保やロックは現れない。

パラメータ変更のフロー

スライダーを操作すると、MainActivity.updateParams(next) が呼ばれる。ここでは変更後の値が再起動を要するもの(出力/入力デバイス・出力用途・走査幅。Params.requiresRestart() が判定する)かどうかも同時に見ているが、シフト量やドライ/ウェットのような大半のパラメータは動作中でも即座に反映できる。updateParams() は service.updateParams(next) を経由して Params.applyTo(engine) を呼び、engine.setShiftCents(channel, cents) のようなセッターへ振り分ける。セッターは nativeSetShiftCents(handle, channel, cents) として JNI を1回だけ越え、ネイティブ側の PrismEngine::setShiftCents() に届く。ここでシフト量はマイク経路と捕獲経路の両方の PitchShifter へ同じ値が流される(走査幅だけが経路ごとに異なるため)。最終的に PitchShifter::setShiftCentsL() が storeClamped() を通して非有限値を無視し、値を [-1200, 1200] セントへ丸め、std::atomic<float> へ memory_order_relaxed で書き込む。ここまでは全て制御スレッド上で完結し、オーディオスレッドを一切待たせない。

オーディオスレッド側では、process() がブロックの先頭で1回だけ centsL_.target = shiftCentsL_.load(memory_order_relaxed) のように読み出す(ブロック内で atomic を何度も読まない設計になっている)。読み出した目標値は SmoothedParam::tick() によって毎サンプル1次指数平滑され、時定数は20ミリ秒である。平滑後の値との差が十分小さくなると current を target へスナップし、それ以降は微小な直流分(デノーマル対策。デノーマルとは浮動小数点数が正規化できないほど0に近づいた状態を指し、CPU によっては通常の演算より大幅に遅くなることがある)を加算しない設計になっている。平滑された値から rate = centsToRatio(cL) = 2^(cL/1200) が毎サンプル再計算され、これが読み出しヘッドの走行速度になる。

この平滑化が正しく働いているかどうかは、シフト量を急変させたときに聴感上のクリックやジップノイズ(パラメータが不連続に変わることで生じる短いプチ音を指す)が出ないことで確認できる。数値的には verify.cpp のグリッチ系検査(4章)が、シフト量を固定した定常状態でのグリッチ検出を行っている。

パラメータの変更は制御スレッドから std::atomic への1回の書き込みで完結し、オーディオスレッドはそれをブロック先頭で読んでから20ミリ秒かけて滑らかに追従する。

ロックが介在しないため、スライダーの操作がオーディオコールバックを止めることはない。

捕獲経路(他アプリの再生音)のフロー

prism-earring は v0.4.0 以降、マイクだけでなく他アプリの再生音も拾える。これは AudioPlaybackCapture(Android が提供する、他アプリの再生音を合法的に横取りできる API を指す)を使うが、Oboe にはこの API が無いため、Java 側の AudioRecord で完結させている。ユーザーが捕獲を有効にすると、MainActivity は MediaProjection(画面/音声キャプチャの同意を管理する Android の仕組みを指す)の同意画面を出し、同意結果を PrismService.startCapture(resultCode, data) に渡す。Android 14 以降はこの同意結果を使って startForegroundWithCaptureType() で mediaProjection 型を含めて前景化し直してから MediaProjectionManager.getMediaProjection() を呼ぶ必要があり、順序を誤ると SecurityException になる。

実際の捕獲は CaptureController が受け持つ。AudioRecord.Builder().setAudioPlaybackCaptureConfig(config) でエンジンの出力サンプルレートに合わせたストリームを開き、専用スレッド(Process.THREAD_PRIORITY_URGENT_AUDIO で優先度を上げている)が約10ミリ秒ごとに record.read() で読み取る。読めたフレームは engine.pushCapture(floatBuf, frames, channels) に渡され、nativePushCapture が GetPrimitiveArrayCritical(配列をコピーせずネイティブ側から直接触れる JNI の機構を指す)でコピーなしにネイティブへ届ける。AudioBridge::pushCapture() はこれを SPSC(Single-Producer Single-Consumer の略で、書き手と読み手がそれぞれ1本のスレッドに限られるリングバッファの形態を指す)リングバッファへ書き込む。書き手は Java の録音スレッドだけであり、write インデックスだけを進めるためロックは要らない。

一方、オーディオコールバック側では AudioBridge::fetchCaptureChunk() がリングから読み出す。読み手はオーディオスレッドだけであり、read インデックスだけを進める。滞留が20ミリ秒(kCaptureCushionMs)に満たない間は無音で待ち、200ミリ秒(kCaptureMaxFillMs)を超えて滞留したら古い分を捨てて遅延が伸び続けないようにする。読み出した音は captureShifter_.process(capInPlanar_, capOutPlanar_, chunk) というマイク経路とは別インスタンスの PitchShifter に通される。走査幅は既定40ミリ秒であり、マイク経路の9.5ミリ秒より広い。この理由は3章末尾で述べる。最後に mixChunk() が「マイク経路 × micGain + 捕獲経路 × captureGain」を合成し、出力ゲインとソフトクリップを経て出力される。捕獲経路の dry/wet は常に1.0固定であり、UI のドライ/ウェット設定は流れない。捕獲経路には「イヤホンから漏れる生音」に相当するものが存在せず、dry 成分は原音そのものの二重再生になってしまうためである。

この経路の健全性は captureUnderruns() / captureOverruns() / captureFillFrames() という診断カウンタで実機確認する。DSP 部分(捕獲用シフタの走査幅40ミリ秒でのピッチ精度)は verify.cpp の testCaptureSweep() が数値的に検証している(4章)。

捕獲経路はマイク経路と完全に独立した PitchShifter を持ち、ロックフリーな SPSC リングバッファで書き手(録音スレッド)と読み手(オーディオスレッド)をつなぐ。

2つの経路は mixChunk() で初めて合流し、そこでゲインとソフトクリップが適用される。

Chapter 3

ピッチシフトのアルゴリズム

prism::PitchShifter がリングバッファと2本の読み出しヘッドだけで、FFT を使わずにピッチシフトを実現する仕組みが分かる。

目的は、入力音の周波数成分をおよそ rate = 2^(cents/1200) 倍にシフトすることである。半音は100セントだが、prism の既定値は-89セントであり、半音ぴったりではない。そのため実装は半音=100セントを決め打ちにせず、任意のセント値から比を計算する centsToRatio() を持つ(BR1.1)。

// BR1.1: セント -> 速度比。半音=100 セントの決め打ちは行わない。
static double centsToRatio(float cents) noexcept {
    return std::exp2(static_cast<double>(cents) / 1200.0);
}

最重要の制約は CLAUDE.md が定める遅延要件である。イヤホンは外界音を完全に遮断しないため、処理音に生音が漏れ込む。この漏れ込みと処理音がずれると唸りや会話の破綻が起きるため、処理部の遅延を10ミリ秒以下に収める必要がある。位相ボコーダ(入力を短時間フーリエ変換して周波数領域でピッチを操作し、逆変換で戻す手法を指す)は音質面では優れるが、一般的な窓長2048サンプル@44.1kHzだけで46ミリ秒かかり、この時点で要件を満たさない。そのため prism は音声経路に FFT を一切使わず、時間領域でリサンプリングするディレイライン型ピッチシフタ(テープヘッド回転方式とも呼ばれる)を採用している。

仕組みの土台はリングバッファ(先頭と末尾がつながった環状の配列を指し、書き込み位置が末尾に達すると先頭へ折り返す)である。process() は毎サンプル、入力を channel_[ch][writeIndex_] へ書き込んでから writeIndex_ を1つ進める(wrapIndex() が容量を超えたら折り返す)。読み出しは書き込み位置から一定サンプル遅れた場所を、線形補間(隣り合う2サンプルの値を実数位置の小数部で按分して滑らかな値を作る手法を指す)を使う readAt() で行う。この「遅れ」を lag と呼び、読み出しヘッドは lag を毎サンプル drift = 1 - rate だけ進める。rate が1未満(下げ方向)のときは drift が正になり、lag は徐々に増える。これは読み出し位置が書き込み位置に対して相対的にゆっくり進むことを意味し、結果として入力を引き伸ばして読むことになり、ピッチが下がる。図5に、既定の-89セント・48kHz でのある瞬間の位置関係を示す。baseOffset(8サンプル、線形補間で前後2サンプルを常に参照できるようにする安全マージン)から始まり、走査幅 sweep(既定9.5ミリ秒、456サンプル@48kHz)ぶん先まで lag が動ける範囲になっている。

lag が走査域の端(下げ方向では baseOffset + sweep = downTriggerLag_)に達すると、そのままでは読み出し位置が未来へ突き抜けてしまうため、跳躍(ヘッドを手前に戻す操作)が起きる。跳躍量が固定だと、戻った先の波形が元の波形と位相的にずれ、出力スペクトルにノイズが乗る。これを避けるため prism は跳躍のたびに正規化相互相関(2つの信号波形がどれだけ似た形をしているかを、大きさの違いを正規化した上で数値化する手法を指す。WSOLA という時間領域ピッチ/タイムストレッチ手法で使われる考え方と同じである)を計算し、直近512サンプル(kCorrelationLength)と最もよく一致する跳躍量を [0.35×最大跳躍量, 最大跳躍量] の範囲で探す startJump() を実装している。最良の跳躍量が見つかると、新しい読み出しヘッドがそこに置かれ、旧ヘッドから新ヘッドへ定振幅(等パワーではなく単純な線形補間で混ぜる方式を指す)のクロスフェードが始まる。等パワーではなく定振幅を選んだ理由は、相関で選んだ2本のヘッドはほぼ相関した波形を読んでいるため、等パワー合成だと振幅が最大3dB膨らんでしまうためである。図6に、下げ方向での lag の時間変化(のこぎり波状に増加しては跳躍で戻る様子)とクロスフェード区間を示す。

シフト範囲は当初の契約(下げ専用、-150〜0セント)から±1200セント(上下1オクターブ)へ拡張されている(D-G、5章で詳述)。rate が1を超える上げ方向では drift が負になり、lag は逆に減っていく。走査の向き・跳躍の向き・相関探索の向きはすべて下げ方向と反転する。加えて上げ方向だけの制約がある。クロスフェード中は旧ヘッドも lag を進め続けるため、上げ方向では旧ヘッドの lag がどんどん小さくなり、baseOffset を割り込んで「まだ書き込んでいない未来」を読みにいく危険がある。これを避けるため、上げ方向の走査域全体を guard(sweep/4)だけ持ち上げてあり、その帯が旧ヘッドの走行余地になる。図7に上げ方向での lag の時間変化とガード帯を示す。上げ方向の設計値遅延は baseOffset + guard + sweep/2 となり、下げ方向の baseOffset + sweep/2 より長くなる(既定条件・48kHzでそれぞれ7.29ミリ秒と4.92ミリ秒であり、README の実測ではしきい値検出込みで5.17ミリ秒である)。いずれも10ミリ秒予算には収まっている。

getLatencySamples() が返す設計値遅延は、lag が走査区間を一様に走査するという前提のもとでの平均値であり、baseOffset + sweep/2(上げ方向は + guard)という式になっている。これは3章冒頭で述べた10ミリ秒制約に対する実装側の答えであり、4章の数値検証で実測される。

double getLatencySamples() const noexcept {
    if (!prepared_) return 0.0;
    const float cl = shiftCentsL_.load(std::memory_order_relaxed);
    const float cr = shiftCentsR_.load(std::memory_order_relaxed);
    const double base = (cl > 0.0f || cr > 0.0f) ? upTriggerLag_
                                                 : static_cast<double>(kBaseOffsetSamples);
    return base + 0.5 * static_cast<double>(sweepSamples_);
}

最後に、平滑化とデノーマル対策についても触れておく。process() はブロックの先頭で shiftCentsL_ などの std::atomic を1回だけ読み、SmoothedParam::tick() が毎サンプル1次指数平滑(時定数20ミリ秒)をかける。目標値との差が閾値(kSnapCents や kSnapUnit)を下回ると current を target へスナップし、以後は加算をやめる。スナップしない通常時は微小な直流分 kDenormalGuard(1e-20)を加算し続けており、これは値がゼロへ収束していくときに CPU がデノーマル数を扱って処理が遅くなることを防ぐためのものである。

この仕組み全体が正しく動いているかどうかは4章の数値検証(FFT ピーク比によるピッチ精度、インパルス応答による遅延、隣接差分によるグリッチ検出)で確認しており、いずれもソースコードから独立したオフラインの検証プログラムで行われる。

prism::PitchShifter は FFT を使わず、2本の読み出しヘッドと正規化相互相関による跳躍先選択、定振幅クロスフェードだけでピッチシフトを実現している。

この選択は音質より遅延を優先した結果であり、シフト量が-89セントと小さいために跳躍によるアーティファクトも目立ちにくい。上げ方向への拡張は走査域の向きと跳躍の向きをすべて反転させる形で後から追加された。

Chapter 4

数値検証

verify/verify.cpp がピッチ精度・遅延・グリッチ・ヒープ確保の4項目をどう測っているか、そして実測値がどうだったかが分かる。

目的は、耳で聴いて確認するだけでなく、DSP コアの振る舞いを数値で検証できる形にすることである。team.md が定める本プロジェクトのマージ条件は、この4つの数値検証がすべて緑であることである。

検証プログラム自身も CLAUDE.md の制約に従っており、外部ライブラリを使わない。ピッチ精度検証に必要な FFT のために、検証プログラム側だけに自前の radix-2 FFT(fftRadix2())を実装している。これは DSP コア(音声経路)に FFT を持ち込まないという制約と矛盾しない。検証はオフライン(ファイル入出力なしでメモリ上のバッファに対して行う)で完結しており、clang++ だけでビルドできる。

ピッチ精度は testPitch() / testPitchAt() が担う。110・440・3520 Hz の正弦波を入力し、ウォームアップ(0.6秒)を空けてから32768サンプル(kFftSize)をハン窓 + FFT + 放物線補間で解析し、支配的なピークの周波数を求める dominantFrequency() を使う。出力ピークと入力周波数の比が、期待比 2^(cents/1200) に対して ±0.5%(kPitchRelTolerance)以内であることを判定する。既定の-89セントだけでなく、testShiftRange() が-1200〜+1200セントの範囲を複数点で検査している。

遅延は testLatency() が担う。振幅1.0の単位インパルス(1サンプルだけ1.0で残りは0の信号を指す)を入力し、出力が閾値(kLatencyThreshold = 0.05、-26dBFS相当)を初めて超えるサンプル番号を数える。この実測値が10ミリ秒予算(kLatencyBudgetMs)以内であること、かつ getLatencySamples() が返す設計値との差が許容差以内であることの両方を判定する。

グリッチは testGlitch() / testGlitchAt() が担う。440Hz の正弦波を5秒間流し、隣接するサンプル間の差分が期待される最大スロープ(2π・f・比・振幅/fs)の3倍(kGlitchSlopeFactor)を超える箇所を数える。先頭250ミリ秒(kGlitchWarmupSec)はウォームアップとして除外し、それ以外で不連続点が0件であることを求める。

ヒープ確保はグローバルの operator new / operator delete を差し替えて呼び出し回数を数える方式(g_allocCount)で検証している。runBlocks() は計測区間の前後でこのカウンタの差分を取り、0でなければ assert で止める。README によれば、この確保検出は -O2 では対になった new/delete がコンパイラに省略されうるため -O0 ビルドが正となり、build.sh は両方のビルドを実行して全緑を要求する。

constexpr double kExpectedRatio = 0.95;          // BR2.1: 418/440
constexpr double kPitchRelTolerance = 0.005;     // BR2.1: ±0.5%
constexpr double kLatencyBudgetMs = 10.0;        // BR2.2 / NFR-1
constexpr double kGlitchSlopeFactor = 3.0;       // BR2.3: k = 3.0
constexpr int kFftSize = 32768;                  // N=32768

ピッチ精度は、シフト定義域 ±1200 セント(上下1オクターブ)の走査でも最悪1.64セント(0.095%)の誤差に収まっており、許容差 ±0.5%(= ±8.66セント)の1/5程度である。約105Hz未満で精度が落ちるのは3章で述べた「走査幅と最低周波数のトレードオフ」の物理的な帰結であり、90Hzでは−15.4セントの誤差になる。

この検証プログラム自体の信頼性は、build.sh が行う決定論検査(同一バイナリを2回実行して cpu 行を除き完全一致すること)と再現性検査(-O0 と -O2 で検出ピークの差が ±0.015 Hz 以内であること)によって担保されている。

verify.cpp は FFT・インパルス応答・隣接差分・確保カウンタという4種類の数値検証を、外部依存ゼロのまま自動実行できる形にまとめている。

実測ではピッチ誤差が最悪でも1.64セント(許容差8.66セントの1/5)に収まっており、既定の-89セントでの遅延は5.17ミリ秒と10ミリ秒予算の半分程度である。

Chapter 5

設計文書からの逸脱

承認済みの設計文書と実装が食い違っている箇所と、それぞれがなぜそうなったかが分かる。

目的は、AI が生成した実装のうち「意図的に設計を変えた箇所」を記録し、後から読む人(開発者自身を含む)が意図せぬ改変と区別できるようにすることである。すべて README.md の「設計からの逸脱」節に詳しい根拠とともに記載されている。

制約は、元の設計文書(aidlc/ 配下)自体は編集しないというルールである。そのため逸脱は文書を書き換える形ではなく、README にログとして残す形を取っている。

D-A(最重要)遅延スイープをクロスフェード窓長から分離した

元の設計ではヘッドの遅れの振幅がクロスフェード窓長から決まる式(D = (1-rate)×window)になっていたが、この式のままだとピッチ精度検証が原理的に通らないことが判明した。ヘッドの跳躍は読み出し位相を入力位相へ再同期させてしまうため、出力スペクトルのピークが入力周波数の近くに戻ってしまう帯域が生じる。そこで遅れの振幅を独立した設計定数 kSweepMs(既定9.5ミリ秒)として持たせ、10ミリ秒の遅延予算の中で最も低い周波数まで正しくシフトできる値を選んでいる。

D-A2 走査幅 sweep を prepare() の引数にした

マイク経路は生音の漏れ込みがあるため10ミリ秒予算(既定9.5ミリ秒)を守る必要があるが、捕獲経路には比較対象になる生音が存在しないため、跳躍間隔(sweep ÷ |1-比|)を伸ばしてアーティファクトを減らせる40ミリ秒を採用している。

D-B 跳躍量を波形同期(正規化相互相関)で選ぶようにした

元の設計では跳躍量は蓄積した遅れの分だけ固定だったが、低い周波数では走査幅がちょうど1周期分しかなく、固定跳躍では位相が合わない。相関で最良の跳躍量を探すことで、110Hzから6kHzまで誤差1セント未満に収めている。

D-C クロスフェードを等パワーから定振幅(線形)に変更した

等パワー合成は2系統が無相関であることを前提にした式だが、D-B によって2本のヘッドは波形同期して相関するようになったため、等パワーのままだと振幅が最大3dB膨らんでトレモロ(周期的な音量の揺れを指す)が生じてしまう。

D-D getLatencySamples() の式を変更した

遅れがスイープ区間を一様に走査するという前提のもとでの平均値(baseOffset + sweep/2)に変更した。D-A で遅延スイープの定義が変わったことに伴う変更であり、判定式(許容差)自体は変えていない。

D-E クロスフェード位相を左右チャンネル共有から独立に変更した

左右のシフト量(shiftCentsL/R)が独立に設定できる仕様のため、遅れの蓄積速度もチャンネルごとに違ってよく、共有のままでは矛盾が生じるためである。

D-G シフト範囲を ±1200セント(上下1オクターブ)へ拡張した

契約の -150〜0セント(下げ専用)から拡張したもので、「上げ方向も使いたい」という利用者要望に応えている。読み出し速度が1を超える場合に走査・跳躍・相関探索の向きをすべて反転させ、上げ方向専用のガード帯を追加する必要が生じた(詳しくは3章)。

D-H クロスフェード窓長の上限を200ミリ秒へ広げた

契約の100ミリ秒から広げ、あわせて跳躍量の8倍という別の上限キャップ(runLimit)を撤廃した。このキャップが下げ方向では常により小さい制限として効いてしまい、窓長100ミリ秒を指定しても実効的には76ミリ秒程度に丸められていたことが分かったためであり、撤廃後は「最小と最大で違いが聞き分けられない」という利用者からの報告が解消した。

これらの逸脱はいずれも README.md に実測値つきで記録されており、たとえば D-A の主張(元設計ではピッチ精度検証が通らない)は「110Hzでratio=1.0006、440Hzで0.9090(いずれもFAIL)」という実測とともに示されている。

設計からの逸脱は、そのほとんどが「元の設計のままでは数値検証(4章)を通過できない」という実測に基づく修正であり、恣意的な変更ではない。

唯一 D-G(シフト範囲の拡張)だけは利用者要望による仕様追加であり、契約文書は未編集のままこの README がその記録を担っている。
